Capture pipeline notes

Working notes on how a browser extension stitches a page that is taller than the screen — and what breaks along the way.

💡 This fixture is deliberately tall. The whole point is to force the capture into many viewport slices, so any seam or scroll-position bug shows up instead of hiding behind a short page.

Why slicing is unavoidable

A browser cannot hand you an image of a page that does not fit on your screen. There is no API for it. The Page.captureScreenshot endpoint you may have read about in the DevTools Protocol only works for the viewport, and the deprecated captureVisibleTab extension API behaves the same way.

So tools do what you would do if you had to photocopy a newspaper column by column: scroll to a position, take a picture of what is on screen, scroll a little further, take another picture, and then paste the pictures together.

The three things that go wrong

  1. Off-by-one scroll. The browser clamps the last scroll position. If the tool assumes its requested scroll offset was honoured, the final slice overlaps the previous one and the stitched image has a doubled band.
  2. Fixed elements. A sticky header is painted into every slice. Stitch them naively and the header appears dozens of times down the page.
  3. Late-loading content. Images below the fold have not started downloading. Slice them before they paint and you get empty rectangles.

Segment arithmetic

Each slice covers exactly one viewport. The number of slices is therefore ceil(pageHeight / viewportHeight) — for a 30 000 px page in an 800 px viewport that is 38 slices, and every one of them costs a scroll, a settle delay, and a round trip to the extension service worker.

That per-slice cost is the dominant term in total capture time, and it is the number that decides whether a capture feels instant or feels broken.

Stitching on a canvas

Service workers have no DOM, so the final composition happens in an offscreen document that owns an OffscreenCanvas. Each slice arrives as a data URL, gets decoded into an ImageBitmap, and is drawn at its page-absolute Y offset.

The crop rectangle is the part that is easy to get wrong. The captured bitmap is in device pixels; the canvas works in CSS pixels. When the device pixel ratio is 2, a crop that forgets to scale silently produces an image that is half the size it should be — or an image where the bottom half of every slice is missing.

const scale = bitmap.width / viewportWidth;
const sy = Math.round((cropTop - viewportTop) * scale);
const sh = Math.round(cropHeightCss * scale);
ctx.drawImage(bitmap, 0, sy, bitmap.width, sh, 0, cropTop, viewportWidth, cropHeightCss);

On the failure that never surfaces

If any coordinate in that call is NaN, drawImage does not throw. It simply draws nothing. The result is a full-size, entirely blank PNG — and a blank PNG still has a plausible file size, so a test that only asserts "the file is bigger than 5 KB" passes happily.

That is why the regression suite has to look at pixels, not at byte counts. test pixel-check

Error handling

A capture can fail for reasons that have nothing to do with stitching: the tab was closed, the page navigated, the service worker was evicted mid-run, or the page is simply taller than the memory budget allows.

The last one deserves special treatment. A page past roughly 50 000 CSS pixels needs a canvas that no longer fits comfortably in an offscreen document, and the browser will kill it rather than tell you why. Refusing early with a clear message is strictly better than failing halfway through with a blank canvas.

⚠️ Active refusal beats silent failure. A user who is told "this page is too long, try region capture" can act on it. A user who is handed a 12 MB blank PNG cannot.
