Web font arrives late

The webfont is not requested when the page loads. The test calls window.__shotlyLoadFont() at the same moment it starts the capture, so the font request and the capture race each other.

A capture that does not wait for fonts paints the fallback instead — the text is the right size and the right colour, but the letterforms are wrong, and nobody notices until the image is used somewhere that matters.

What the pipeline has to cover

Between the scroll and the actual pixel grab there is a settle window. The font request has to fit inside it. If the font is requested at the same time the capture starts, the window is exactly what separates the two outcomes.

Why two identical lines

Comparing against a reference image is fragile — antialiasing, subpixel positioning and DPR all shift the bytes. Instead the page contains the same word twice: once asking for the webfont, once explicitly asking for the generic serif. If the webfont applied, the two renderings differ. If it did not, they are the same word in the same font and match exactly.

Failure modes

A capture that runs before the font arrives shows the fallback in both lines. A capture that runs with a font-display of block and no wait shows nothing at all — the glyphs are simply not painted yet, and the band is blank.
